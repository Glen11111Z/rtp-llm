2. 进程模型与启动流程

进程架构

RTP-LLM 使用 multiprocessing.spawn 创建两类进程：

  • Backend Process：加载模型权重，运行 C++ 推理引擎（通过 pybind11 绑定），处理实际的推理计算
  • Frontend Process(es)：运行 FastAPI/uvicorn HTTP 服务，处理请求解析、Tokenize、OpenAI 协议转换等

为什么采用多进程架构

1. GIL 隔离 — 最根本的原因

Backend 进程通过 pybind11 调用 C++ 引擎（libth_transformer.so），涉及大量 PyTorch 张量操作和 CUDA 内核调度。Frontend 进程运行 FastAPI/uvicorn 异步 HTTP 服务器，大量使用 Python asyncio。

如果放在同一进程，Python GIL 会导致：C++ 端释放 GIL 做 CUDA 计算时没问题，但模型加载、权重初始化、Python 侧 tensor 操作会长时间持有 GIL，阻塞所有 HTTP 请求处理；asyncio 事件循环在等待 GIL 时无法处理新连接，导致健康检查超时、请求排队。

2. 故障隔离

ProcessManager（start_server.py:209-245）独立监控 backend 和 frontend 进程的健康状态。如果 Backend 因 OOM、CUDA error、coredump 崩溃，Frontend 进程仍然存活，可以返回 503 而不是整个服务直接消失。反之 Frontend 挂了，GPU 上的模型状态不受影响，可以重新拉起 Frontend。

3. 独立的生命周期与启动时序

Backend 启动非常慢（加载几十 GB 权重到 GPU、初始化 NCCL、JIT 编译 kernel），而 Frontend 启动很快。Frontend 在 uvicorn 启动后通过 _wait_backend_health_ready_impl()（frontend_app.py:94-120）轮询 Backend 的 gRPC health_check。这样 k8s 的 liveness probe（/frontend_health）可以在 Backend 还没 ready 时就返回，避免 Pod 被杀。

4. 多 Frontend 水平扩展

Frontend 可以启动多个实例（frontend_server_count，start_server.py:129-134），共用同一个 Backend。HTTP 解析、tokenize、OpenAI 协议转换都是 CPU 密集的 Python 工作，多个 Frontend 进程可以利用多核并行处理请求，而 Backend 只需要一个进程持有 GPU。

5. PD 分离（Prefill/Decode Disaggregation）支持

start_server.py:217 的 RoleType.FRONTEND 判断说明 Frontend 和 Backend 可以部署在不同机器上。在 PD 分离架构中，Prefill 节点和 Decode 节点是不同的 Backend 进程，Frontend 作为独立角色，通过 gRPC 路由请求到不同的 Backend。

6. 为什么用 spawn 而不是 fork

start_server.py:196 显式设置 multiprocessing.set_start_method("spawn")。CUDA runtime 不支持 fork——如果父进程已初始化 CUDA context，fork 出的子进程会继承损坏的 CUDA 状态，导致不可预测的崩溃。spawn 创建全新的进程，确保每个进程独立初始化自己的 CUDA context。

总结：这个设计本质是关注点分离 + 资源隔离。GPU 推理和 HTTP 服务是两种完全不同的工作负载（一个 GPU-bound + C++ 密集，一个 IO-bound + Python asyncio），放在独立进程中各自可以用最合适的并发模型，互不干扰，且支持独立扩缩和故障恢复。

GenerateStream 与 StreamGroups：两层抽象的设计原理

GenerateStream — 单个请求的完整生命周期（纵向抽象）

GenerateStream 代表一个用户请求从入队到生成结束的完整状态机。其生命周期跨越数百个 decode step，持有：

  • 全部输入：token ids、generate config、multimodal features
  • 状态机：GenerateStateMachine（WAITING → LOADING_CACHE → RUNNING → FINISHED）
  • KV Cache 资源：StreamCacheResource，管理 block 分配/释放
  • 采样输出：CompleteTokenIds、cum_log_probs
  • Logits Processor：CSR 约束解码等，每个请求独立的状态
  • Beam Search 状态：effective_beam_size_
  • 投机解码 Buffer：propose_stream_、sp_output_buffer_

StreamGroups — 单次 forward 的批处理视图（横向抽象）

StreamGroups 是一次 model.forward() 调用的临时批处理快照。从 NormalExecutor::process() 第一行即可看到：

// NormalExecutor.cc:126
StreamGroups stream_groups(streams);  // 构造后立即使用，函数返回即销毁

它把 Scheduler 给出的 running_streams_ 列表按当前状态分拣成 context_streams_ 和 decode_streams_，并预计算本轮 forward 需要的所有聚合指标（batch size、max_seq_len、token 总数、block 数等），供后续 gatherModelInput、gatherSamplerInput、dispatch 使用。

两者关系是 1:N —— 一个 GenerateStream 参与数百次 StreamGroups（每个 decode step 一次），每次 StreamGroups 是当前这一步所有 running stream 的快照。

为什么 StreamGroups 必须区分 Context Streams 和 Decode Streams

1. Token 数量差异巨大

从 NormalModelInputGatherer.cc 可以看到两者的根本不同：

// processDecodeStreams (line 253):
ctx.merged_tokens[ctx.batch_idx] = currentTokens[0];  // 每个 decode stream 只有 1 个 token

// processContextStreams (line 293):
memcpy(ctx.merged_tokens + ctx.token_idx, input_tokens.data(),
       input_tokens.size() * sizeof(int));  // 每个 context stream 有几百~几千个 token

Decode stream 的 currentExecuteTokens() 返回 1 个 token（上一步刚生成的），输入是增量的；Context stream 返回完整的 input sequence（减去 prefix cache 复用的部分），输入是全量的。这直接决定了 combo_tokens 的拼接方式、lm_output_indexes 的计算、position ids 的生成逻辑都完全不同。

2. Attention 计算路径与复杂度完全不同

在 Transformer 模型的 Attention 层中，Context stream 走 Flash Attention（self-attention），Decode stream 走 Paged Attention（增量 attention），两者的 CUDA kernel、内存布局、cu_seqlens 构造方式完全不同。

Context (Prefill)Decode
Query 数量n（完整输入序列）1（当前新 token）
KV 数量nn（KV Cache 中的历史 token）
Attention 矩阵[n, n][1, n]
计算复杂度O(n²)O(n)
瓶颈特征Compute-boundMemory-bound
Attention KernelFlash AttentionPaged Attention

Decode 阶段 Attention 为 O(n) 的原因 — Causal Mask + KV Cache

在 Causal（因果）Attention 中，每个 token 只能 attend 到它自己和它之前的 token，不能看未来。这意味着当 decode 阶段生成新 token tn 时，旧 token t0~tn-1 的 attention 输出不会因为 tn 的出现而改变（因为 causal mask 保证它们看不到 tn）。

因此旧 token 在 prefill 阶段算过的结果仍然有效，不需要重新计算。唯一需要计算的就是 tn 这一个新 token 的 attention 输出——用 tn 的 query 去 attend KV Cache 中 t0~tn 的所有 key/value：

// Decode 阶段每一步的 Attention 计算:
Q: [1, d]      ← 当前生成的 1 个 token 的 query
K: [n, d]      ← KV Cache 中的 n 个历史 key
V: [n, d]      ← KV Cache 中的 n 个历史 value

1. QK¹: [1, d] × [d, n] = [1, n]  → O(n·d) = O(n)  (d 是常数，通常 128)
2. softmax: [1, n]              → O(n)
3. score × V: [1, n] × [n, d] = [1, d]  → O(n)
总计: O(n)

对比 Prefill 阶段：完整的 n 个 token 同时作为 query，QK^T 产生 [n, n] 的 attention 矩阵，计算量 O(n²)。

KV Cache 的本质是用显存（存储历史 K/V）换计算（避免重算）。如果不用 KV Cache，每生成一个新 token 都要重新过完整序列，生成 N 个 token 的总计算量是 O(1² + 2² + ... + N²) = O(N³)。有了 KV Cache，每步只算 1 个 query token，总计算量降为 O(1 + 2 + ... + N) = O(N²)。

3. KV Cache 操作语义不同

Context stream 需要一次写入整个序列到 KV cache（初始化 blocks），而 decode stream 只需要追加 1 个 token 到已有 blocks。对应 kv_cache_update_mapping 的构造也不同（decodeBlockUpdateCopyNum vs contextBlockUpdateCopyNum 分别统计）。

4. 调度策略依赖此分类

FIFOScheduler::evaluateRunningMemory()（FIFOScheduler.cc:129-131）需要知道当前 running 中有多少 decode batch（占用显存但计算量小）vs context batch（计算量大但一次性的），以做出正确的显存预算和 batching 决策。StreamGroups 的 totalDecodeBatchSize() 和 totalContextBatchSize() 直接服务于此。

5. Sampler 输出分发路径不同

NormalOutputDispatcher 在分发 sampler 输出时：

  • Context stream：第一次输出 token，需要设 *is_context_stream_ = false（转为 decode），同时处理 beam search 初始化（从 batch_size=1 扩展到 num_beams）
  • Decode stream：追加 token，检查 EOS/stop words，更新 logits processor 状态

6. Continuous Batching 核心设计

整个分类本质服务于 Continuous Batching（iteration-level scheduling）：

Scheduler 每一轮调度:
  running_streams_ = [已在 decode 的 stream A, B, C] + [刚从 waiting 进来的新 stream D]
                                                         ↑
                                                    D 是 context stream (第一次执行，要跑 prefill)

StreamGroups 分类后:
  decode_streams_  = [A, B, C]     →  每个只需 forward 1 个 token
  context_streams_ = [D]           →  需要 forward 完整 input sequence

model.forward() 一次调用同时处理两类:
  combo_tokens = [tokenA, tokenB, tokenC, tokenD_0, tokenD_1, ..., tokenD_N]
                  ← decode 在前 →           ←  context 在后  →

allStreams() 返回 decode 在前、context 在后的顺序（StreamGroups.h:150-153），这个顺序在整个 pipeline 中保持一致——gather、forward、sample、dispatch 都按同一 batch 维度排列。
